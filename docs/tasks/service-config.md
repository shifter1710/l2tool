# Задачи: редактор сервисов диагностики на сайте

Самодостаточный план для работы в отдельных чатах. Ветка:
`feature/service-config` (создана от `dev`).

Цель — превратить страницу «Настройки источников» в полноценный редактор
источников диагностики: блоки и **сами продукты** добавляются, изменяются,
включаются/выключаются и удаляются с сайта, потому что состав сервисов, по
которым ищем логи, будет меняться.

## Как работать с задачей (для нового чата)

1. Переключиться: `git checkout feature/service-config`.
2. Прочитать: эту задачу, разделы «Контекст» и «Ограничения», затем файлы
   из списка задачи.
3. Сделать задачу целиком, прогнать проверки (см. ниже), коммит, push,
   PR в `dev`.

## Контекст: что уже есть

- `core/dynamic_sources.py` — хранилище `diagnostic_sources.json`
  (версия 1: `managed_products` + `sources[]`), атомарная запись с правами
  0600 и блокировкой `_WRITE_LOCK`; валидация блоков (`validate_source`),
  импорт с пропуском дубликатов, сборка ссылок (`build_source_links`,
  `build_product_links`). Уровни: `number` (подстановка номера, стратегии
  raw / national / hash16) и `uuid` (uuid / compact_uuid).
- `webapp.py` — роуты `/settings`, `/settings/source`,
  `/settings/source/delete`, `/settings/import`, `/settings/export`;
  отрисовка через `product_groups()`.
- `templates/settings.html` — форма добавления, карточки-редакторы блоков,
  импорт/экспорт файла.
- `core/products.py` — пять зашитых продуктов (recording, secretary, calls,
  noise, assistant); первый пользовательский блок продукта переводит его
  в `managed_products`, и в вебе работает динамическая конфигурация вместо
  статического профиля `config.toml`.
- CLI (`gtool.py`) работает только со статическими сервисами из
  `services/registry.py` и `config.toml` — это отдельный мир, его не трогаем.

## Ограничения (нарушать нельзя)

- Данные — только локальные (`diagnostic_sources.json`, права 0600,
  атомарные записи); никаких БД и внешних хранилищ.
- Ссылки с токенами/ключами отклоняются (уже реализовано — не сломать).
- Лимит файла конфигурации 2 МБ; импорт ≤ 500 блоков.
- CSP: без внешних скриптов/стилей; всё работает без JS.
- Обратная совместимость: старый `diagnostic_sources.json` (версия 1) должен
  открываться без ручной правки; CLI не должен сломаться.

## Проверка (после каждой задачи)

```bash
.venv/bin/python -m pytest -q
.venv/bin/python -m ruff check .
.venv/bin/python webapp.py --no-browser   # ручная проверка /settings
```

экспорт/импорт, старый файл конфигурации открывается, CLI-сценарий из README
работает по-прежнему.

## Задача 1. Редактируемые продукты

Проблема: список продуктов зашит в `core/products.py` — добавить свой продукт
или убрать ненужный с сайта нельзя.

- Схема v2 в `diagnostic_sources.json`: `products: [{key, title, color?}]`
  вместо массива строк `managed_products`. Миграция v1 → v2 при чтении
  (автоматически, с сохранением файла при первом изменении).
- `core/products.py`: `available_products()` / `product_title()` /
  `resolve_product_modules()` читают продукты из хранилища; встроенные пять —
  значения по умолчанию, когда файла нет. Пользовательский продукт не имеет
  статических модулей — работает только через динамические блоки.
- UI на `/settings`: секция «Продукты» — добавить (ключ + название + цвет
  монограммы), переименовать, удалить (удаление запрещено, пока у продукта
  есть блоки — сначала предложить удалить/перенести их).
- Валидация ключа: латиница/цифры/дефис, уникальность; клавиши встроенных
  продуктов менять нельзя (на них может ссылаться CLI и README).

**Готово, когда:** можно создать продукт «Запись МСК», добавить в него блоки,
провести диагностику по нему и удалить продукт; старый json открывается;
`tests/test_dynamic_sources.py` + новые тесты продуктов зелёные; CLI не
изменился в поведении.

## Задача 2. Включение/выключение, дублирование и порядок блоков

Проблема: временно убрать блок можно только удалением; порядок ссылок
зафиксирован порядком добавления.

- Поле `enabled: true|false` у блока: выключенный не участвует в
  `build_product_links` и показывается в настройках приглушённым с бейджем
  «Выключен». Переключение — одним кликом, без входа в редактор.
- «Дублировать блок» — копия с суффиксом «(копия)» и новым id, сразу в
  режиме редактирования.
- Порядок: кнопки «Выше/Ниже» на карточке (drag-and-drop не нужен — без JS
  должно работать); порядок в файле = порядок ссылок в результатах.
- Массовые операции для уровня продукта: «включить все / выключить все».

**Готово, когда:** выключенный блок исчезает из диагностики, но остаётся в
настройках; порядок ссылок меняется с сайта; всё работает без JS;
тесты на enabled/порядок/дублирование добавлены.

## Задача 3. Проверка ссылки и предпросмотр подстановки

Проблема: чтобы понять, что блок настроен верно, приходится сохранять его и
запускать диагностику с настоящей заявкой.

- В форме блока (существующую и новую) — блок «Проверка»: поле «тестовый
  номер или UUID» + кнопка «Проверить» (POST на тот же `/settings/source`
  c `preview=1` или отдельный роут `/settings/source/preview`).
- Ответ: итоговая ссылка с подставленным тестовым значением и текущим окном
  времени (тот же код, что в `build_source_links`, с `ctx` из тестового
  значения и «сегодня») — read-only, с кнопкой «Открыть в новой вкладке».
- Ошибки подстановки показываются в этом же блоке, без сохранения.

**Готово, когда:** для новой ссылки можно до сохранения увидеть готовый URL
и открыть его; тесты: предпросмотр не пишет в хранилище, показывает ошибку
для ссылки без значения-примера.

## Задача 4. Резервные копии настроек и откат

Проблема: одно неверное изменение/удаление портит всю конфигурацию; сейчас
бэкапы делаются вручную (в корне репозитория уже лежит
`diagnostic_sources.backup-20260903.json` — след этой проблемы).

- Перед каждым изменяющим действием (сохранение, удаление, импорт, правка
  продуктов) — копия `backups/diagnostic_sources.YYYYMMDD-HHMMSS.json`
  (атомарно, 0600). Ротация: последние 20 копий.
- Страница настроек: список копий (дата, количество блоков) и «Откатиться»
  с подтверждением. `backups/` добавить в `.gitignore`.
- В README — раздел про бэкапы настроек.

**Готово, когда:** после удаления блока можно откатиться к предыдущему
состоянию в один клик; старые копии удаляются автоматически; тесты на
ротацию и откат.

## Задача 5. Импорт статических профилей из config.toml

Проблема: часть команды ведёт сервисы в `config.toml` (статические профили,
CLI), часть — в `diagnostic_sources.json` (веб). Конфигурация раздвоена.

- Кнопка на `/settings`: «Перенести сервисы из config.toml» — для каждого
  `[services.<имя>]` с URL создать блок с этим названием в выбранном продукте
  (уровень number, стратегия определяется автоматически как при вставке
  ссылки). Существующие блоки с такой же ссылкой пропускаются (отчёт:
  добавлено / пропущено / ошибки с причинами).
- Это односторонний мост для перехода; `config.toml` не переписывается.

**Готово, когда:** после переноса весь профиль «Запись» воспроизводится
динамическими блоками и даёт те же ссылки; тест с фикстурой config.toml.
