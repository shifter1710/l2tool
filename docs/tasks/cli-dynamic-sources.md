# Задачи: CLI на динамических источниках

Самодостаточный план для работы в отдельных чатах. Ветка:
`feature/cli-dynamic` (создаётся от `dev`).

Цель — устранить раздвоение конфигурации: `gtool.py` сегодня работает
только со статическими `services/registry.py` + `config.toml`, а веб —
с `diagnostic_sources.json`. CLI должен уметь читать динамическую
конфигурацию как основной источник сервисов, оставляя статику как
фолбэк, чтобы привычные сценарии из README не сломались.

## Как работать с задачей (для нового чата)

1. Переключиться: `git checkout dev && git checkout -b feature/cli-dynamic`.
2. Прочитать: эту задачу, разделы «Контекст» и «Ограничения», затем файлы
   из списка задачи.
3. Сделать задачу целиком, прогнать проверки (см. ниже), коммит, push,
   PR в `dev`.

## Контекст: что уже есть

- `gtool.py` — точка входа CLI: `run_ticket`, интерактивное меню продукта,
  `--product`, `--open`, `--window`, `--dry-run`, `--export-case`; коды
  завершения 0/1/2; историю и `*.parsed.json` пишет только при полном
  успехе.
- `services/registry.py` — 11 статических сервисов; модули `modules/`
  строят ссылки из `config.toml`.
- `core/dynamic_sources.py` — чтение `diagnostic_sources.json`,
  `build_source_links(ctx)` возвращает готовые ссылки (заголовок, URL,
  платформа); контекст заявки CLI уже умеет собирать.
- Веб не трогаем: он уже работает с динамическими источниками.

## Ограничения (нарушать нельзя)

- Поведение флагов и коды завершения не меняются; все примеры из README
  продолжают работать дословно.
- Нет `diagnostic_sources.json` (или в нём нет блоков) — CLI работает по
  старой схеме `registry + config.toml`, без предупреждений.
- Есть динамическая конфигурация — она главный источник: меню продукта и
  `--open` оперируют её блоками; статика используется только для сервисов,
  которых в динамике нет.
- Экспорт `--export-case` включает ссылки динамических блоков; политика
  экспорта (без исходного текста, путей и секретов) сохраняется.

## Задача 1. Мост к динамическому хранилищу

- `core/dynamic_sources.py`: при необходимости вынести функцию
  «собрать ссылки блоков для контекста заявки» так, чтобы её использовали
  и веб, и CLI без дублирования (сейчас логика частично в `webapp.py`).
- В CLI: если файл существует — загрузить блоки, построить структуру
  «продукт → блоки»; пустые продукты скрыть из меню.

**Готово, когда:** `--dry-run` с динамическим файлом печатает ссылки
динамических блоков, без файла — статические; тесты на оба режима.

## Задача 2. Меню и `--open` по динамическим блокам

- Интерактивное меню показывает продукты и блоки из динамической
  конфигурации; выбор блока строит ссылку через `build_source_links`.
- `--open` принимает ключи блоков (id или названия); ошибку «неизвестный
  блок» — с перечнем доступных, как сейчас для продуктов.
- `--export-case` и автозапись `*.parsed.json` содержат динамические
  ссылки.

**Готово, когда:** сценарий «вставил заявку → выбрал продукт → открыл
блоки» работает целиком на динамической конфигурации; тесты на `--open`
по id и на сообщение об ошибке.
