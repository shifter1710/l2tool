# Задачи: панель-ранбук «симптом → где смотреть»

Самодостаточный план для работы в отдельных чатах. Ветка:
`feature/runbook-panel` (создаётся от `dev`).

Цель — встроить в веб-интерфейс проверочные маршруты: пользователь выбирает
симптом («запись есть, транскрипта нет») и получает упорядоченный список
шагов — какой диагностический блок открыть и что в нём искать. Шаги
ссылаются на уже настроенные блоки источников и подставляют данные текущей
разобранной заявки. Содержимое ранбука — внутренние знания команды, поэтому
оно хранится в локальном gitignored-файле; в репозитории только формат и
нейтральный пример.

## Как работать с задачей (для нового чата)

1. Переключиться: `git checkout dev && git checkout -b feature/runbook-panel`.
2. Прочитать: эту задачу, разделы «Контекст» и «Ограничения», затем файлы
   из списка задачи.
3. Сделать задачу целиком, прогнать проверки (см. ниже), коммит, push,
   PR в `dev`.

## Контекст: что уже есть

- `core/dynamic_sources.py` — блоки источников `diagnostic_sources.json`:
  у каждого есть `id`, название, продукт; `build_source_links(...)` строит
  ссылки по данным заявки (номер, UUID, окно времени).
- `webapp.py` — роуты `/analyze` и `/secondary`; результаты рендерятся в
  `templates/_results.html` (XHR-фрагмент) и `templates/index.html`.
- `templates/settings.html` — образец локального файла конфигурации с
  импортом/экспортом и правами 0600.
- Сворачиваемые панели без JS — `<details>/<summary>` уже используются.

## Ограничения (нарушать нельзя)

- Содержимое ранбука — только локальный `runbook.json` (gitignored, 0600,
  атомарная запись, лимит 256 КБ); в репозитории — шаблон
  `runbook.example.json` с нейтральным примером.
- CSP `script-src 'self'; style-src 'self'`; всё работает без JS:
  выбор кейса — обычная POST-форма, шаги — серверный рендер.
- Шаг ссылается на блок источника по его `id`; если блока нет в
  конфигурации — шаг показывается как текст без ссылки (не ошибка).
- Никаких обращений наружу, только localhost.

## Задача 1. Хранилище и формат ранбука

- `core/runbook.py`: чтение `runbook.json` из корня. Формат записи:

```json
{
  "id": "no-transcript",
  "symptom": "Запись есть, транскрипта нет",
  "steps": [
    {"source": "<id блока из diagnostic_sources.json>", "note": "что искать"},
    {"source": null, "note": "шаг без ссылки — например, уточнить у абонента"}
  ]
}
```

- Валидация: `id` уникальны, `symptom` до 200 символов, `note` до 500,
  не более 50 кейсов и 15 шагов в кейсе. Битый файл = пустой ранбук,
  ошибка в лог, приложение работает.
- `.gitignore`: `runbook.json`; шаблон `runbook.example.json` — в корень.

**Готово, когда:** приложение стабильно с файлом/без/битым; тесты на
валидацию и лимиты.

## Задача 2. Панель на главной и выбор кейса

- На `index.html` под формой — свернутая `<details>`-панель «Куда смотреть?»
  со списком симптомов (кнопка-форма: симптом + текст уже разобранной
  заявки из скрытых полей, чтобы не терять контекст).
- Роут (например, `/runbook`) рендерит шаги выбранного кейса: для шагов с
  `source` — ссылка, построенная `build_source_links` по данным заявки
  (номер/UUID/время), плюс `note`; для шагов без — просто текст.
- Если заявка ещё не разбиралась — шаги показываются, но вместо ссылок
  пометка «сначала разберите заявку».

**Готово, когда:** кейс открывается и без JS; ссылки используют данные
последнего разбора; отсутствующий блок источника не ломает страницу; тесты
на рендер шагов.

## Задача 3. Управление кейсами на странице настроек

- Секция «Ранбук» на `/settings`: список кейсов, добавление/правка/
  удаление (симптом + шаги), выбор `source` — выпадающий список блоков из
  текущей конфигурации источников.
- Импорт/экспорт `runbook.json` по образцу источников; перед изменениями —
  копия в бэкапы (если задача 4 плана service-config уже влита —
  использовать его механизм).

**Готово, когда:** кейс можно завести с сайта целиком; тесты на CRUD
и импорт/экспорт.
