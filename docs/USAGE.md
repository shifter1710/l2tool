# Сценарии работы l2tool

Подробные сценарии веб-интерфейса: стандартный разбор заявки, экспорт
кейса в ZIP, вторичная диагностика записи по UUID, пакетная обработка
потерянных звонков и история звонков из баланса. Обзор проекта и быстрый
запуск — в [README](../README.md), устройство сервиса — в
[ARCHITECTURE.md](ARCHITECTURE.md).

## Стандартный сценарий работы

1. Откройте `http://127.0.0.1:8765`, вставьте текст заявки в поле на
   главной, выберите продукт и окно поиска (по умолчанию 60 минут).
2. Нажмите **«Разобрать заявку»** (или Ctrl+Enter в поле заявки).
3. Проверьте блок «Распознанные данные»: номера А и Б с хешем для поиска
   в логах BFF, дата и время, регион с UTC-смещением. Что-то не так —
   заполните нужное поле в форме «Если что-то распознано неверно» под
   результатами и нажмите «Пересобрать результат»; исходный текст заявки
   не меняется.
4. Открывайте диагностические ссылки или копируйте их одной кнопкой.

Поведение по умолчанию:

- номера нормализуются к формату `7XXXXXXXXXX`, даты и время — к
  местному времени региона из заявки;
- если найдена только дата звонка, поиск идёт по интервалу 08:00–20:00,
  точное время можно задать календарём в основной форме или правкой поля
  «Дата и время»;
- совпадения из локальной истории показываются под результатами;
- проблемы разбора (нераспознанный номер А, неизвестное время) не мешают
  диагностике, пока распознан номер клиента, — они выводятся
  предупреждениями;
- успешные разборы сохраняются в `history/` только при включённой
  галочке «Сохранить успешный результат в локальную историю».

Если в заявке нет даты и времени, ссылки всё равно построятся — диапазон
возьмётся из настроек блока, а в предупреждениях отметится, что время
не найдено.

## Экспорт кейса в ZIP

Кнопка **«Скачать ZIP кейса»** в заголовке панели «Распознанные данные»
скачивает архив `case-ГГГГ-ММ-ДД-ЧЧММСС.zip` с двумя файлами:

- `case.json` — структурированный разбор заявки для последующей передачи
  в `l2-local-ai`;
- `case.md` — человекочитаемая сводка тех же данных (поля кейса и ссылки).

Экспорт повторяет разбор текущей заявки тем же продуктом и окном, что и
основная форма, но ничего не записывает на диск сервера: архив собирается
в памяти и сразу отдаётся браузеру.

`case.json` содержит нормализованные идентификаторы (`identifiers`),
дату и время события (`event`), интерпретацию (`interpretation`),
регион (`location`), выбранные сервисы и сформированные ссылки
(`search`) и служебные поля (`source`, `schema_version: 1`). В него не
попадают исходный текст заявки, необработанные телефонные поля,
абсолютные локальные пути, содержимое конфигурации, токены, cookies и
переменные окружения.

JSON-файлы кейсов могут содержать номера клиентов и внутренние ссылки —
не коммитите их в Git.

## Вторичная диагностика записи по UUID

После первичной диагностики продукта «Запись», когда в логах найден UUID
звонка, заполните поле «UUID звонка» в блоке «Вторичная диагностика» под
результатами и нажмите **«Запустить второй этап»**:

- **Только MGW** — поиск записи в `mgw.service`;
- **Вся цепочка: MGW → VSS/CRS → CRS → Collector** — проверка всей
  цепочки обработки записи.

Динамическим продуктам доступны их блоки уровня «Поиск по UUID». UUID
проверяется перед созданием ссылок. Диапазон Loki строится по времени из
заявки; если оно явно пропущено, используется последний час.

## Пакетная обработка потерянных звонков

Панель «Потерянные звонки» на главной обрабатывает табличную выгрузку
(XLSX, XLSM, CSV, TSV) и отдаёт готовый XLSX со ссылками. В исходной
таблице должны присутствовать столбцы:

- `Номер пользователя`;
- `Номер другой стороны`;
- `Старт звонка` — время уже должно быть в UTC;
- `Продолжительность звонка`;
- `Направление звонка` — `in`/`out`, `входящий`/`исходящий` и их английские
  варианты.

В очищенной таблице остаются только пять перечисленных столбцов и три
кликабельные колонки: `Zapis`, `SIP stack prod` и `MGW`. Абонентом всегда
считается `Номер пользователя` из первого столбца; он используется как
`msisdn` во всех трёх ссылках. Для `SIP stack prod` время из таблицы
переводится из UTC в московское. Для всех трёх ссылок задаётся одно окно:
от двух минут до старта звонка до полутора часов после него. Ссылка `MGW`
ищет в логах `mgw.service` оба номера без ведущей `7`. Звонки, которые
старше 5 суток (120 часов) относительно текущего времени UTC, полностью
исключаются из результата. Строки с некорректными номерами или временем
сохраняются без ссылок и перечисляются в предупреждениях.

## История звонков из истории баланса

Отдельный сценарий для выгрузки, которую формирует внешний скрипт
детализации из истории баланса. Вставьте её в панель «История звонков ·
из истории баланса» на главной, укажите номер клиента (msisdn) и продукт —
l2tool строит диагностические ссылки **по каждому звонку**.

Скрипт выдаёт записи из двух строк: диапазон времени с длительностью и
строка участников через стрелку — слева звонящий:

```text
08.09.2026 12:45:09-12:45:13 (0:00:04)
79991000004 → 79991230001 ← 79991234567 (занято)

08.09.2026 13:58:41-14:00:23 (0:01:42)
79991234567 → 79991000005
```

Что учитывает разбор:

- **«А → Б ← В (условие)» — звонок с переадресацией.** А — реальный
  звонящий, Б — номер, на который звонили (сервисный, в ссылках не
  участвует), В — номер клиента, на который ушёл звонок; условие
  («занято», «нет ответа») сохраняется как метка.
- Направление обычного звонка «А → Б» определяется по номеру клиента
  (msisdn): клиент слева — исходящий, справа — входящий. Без msisdn
  номер клиента выводится как самый частый участник выгрузки.
- Короткие коды (0900) подставляются в ссылки как есть.
- Прежний событийный формат (заголовок события, стрелка и
  `Duration: N SECOND`, тип звонка «Цифровой»/«VoLTE») тоже разбирается —
  старые выгрузки остаются совместимы, тройки переадресации в них
  схлопываются в один звонок.

Каждый звонок получает раскрывающуюся карточку со ссылками и метками:
цифровой (MyConnect), VoLTE, условие переадресации, Секретарь. По
умолчанию выводится не больше 50 звонков (`call_history.max_calls` в
`config.toml`). Номер клиента необязателен, но без него ссылки строятся
только по номеру собеседника.

Номера Секретаря настраиваются на странице «Настройки источников» — панель
«История звонков · номера Секретаря», по одному номеру на строку. Список
хранится в `diagnostic_sources.json`, участвует в экспорте/импорте и
резервных копиях настроек. Пока на сайте ничего не сохраняли, работает
фолбэк — секция в `config.toml`:

```toml
[call_history]
secretary_numbers = ["79991230999"]
```

После первого сохранения на сайте (даже пустого списка) приоритет у
настройки сайта — в форме она подставлена предзаполненной, так что первое
сохранение переносит номера из `config.toml` автоматически.
