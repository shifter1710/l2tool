# l2tool

Локальный инструмент диагностики заявок L2: веб-интерфейс и CLI. Разбирает
текст заявки, нормализует номера, дату, время и регион, после чего формирует
готовые ссылки на Grafana и OpenSearch. Сам инструмент не обращается к этим
системам по API — ссылки открываются в браузере пользователя.

Подробное описание устройства сервиса — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md),
план развития веб-интерфейса — в [docs/UI_PLAN.md](docs/UI_PLAN.md).

## Быстрый запуск

Скачайте архив исходного кода со страницы
[Releases](https://github.com/shifter1710/l2tool/releases) (или склонируйте
репозиторий) и запустите:

- **Linux / macOS** — `./start.sh`
- **Windows** — `start.bat` (двойной клик или из терминала)

Нужен только установленный Python 3.10+. При первом запуске скрипт сам создаст
виртуальное окружение `.venv`, установит зависимости и откроет браузер на
`http://127.0.0.1:8765`; повторные запуски стартуют мгновенно. Параметры
`webapp.py` передаются скрипту напрямую: `./start.sh --port 9000`,
`start.bat --no-browser`.

## Требования

- Python 3.10 или новее (CI запускается на Python 3.12)
- доступ к экземплярам Grafana и OpenSearch, настроенным для вашего окружения

Создайте виртуальное окружение и установите зависимости:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

## Локальный веб-интерфейс

Запустите:

```bash
.venv/bin/python webapp.py
```

Браузер откроется на `http://127.0.0.1:8765`. В интерфейсе можно:

- вставить заявку и выбрать профиль продукта;
- проверить распознанные номера, время и регион;
- исправить отдельные поля, не меняя исходный текст;
- открыть сформированные ссылки Grafana и OpenSearch;
- отдельно запустить настроенные блоки второго уровня по UUID;
- обработать локальную выгрузку потерянных звонков и скачать готовый XLSX.

Раздел «Настройки источников» — это конструктор диагностических блоков. Блоки
можно добавлять, переименовывать, переносить между продуктами и уровнями
«Поиск по номерам» / «Поиск по UUID», а также удалять. Для настройки достаточно
вставить готовую ссылку Grafana или OpenSearch с тестовым номером либо UUID.
l2tool определит тип ссылки и способ подстановки, а затем будет заменять пример
данными разобранной заявки и актуальным временным диапазоном.

Настройки веб-интерфейса хранятся локально в `diagnostic_sources.json`. После
добавления первого пользовательского блока для продукта он заменяет прежний
профиль `config.toml` в веб-интерфейсе. Сам `config.toml` сохраняется для CLI и
обратной совместимости.

Готовую пользовательскую конфигурацию можно добавить на странице настроек из
файла `diagnostic_sources.json`. Импорт сначала проверяет все блоки, затем
добавляет новые к существующим и пропускает точные дубликаты. Там же можно
скачать текущую конфигурацию для переноса на другой компьютер.

Сервис принимает соединения только с этого компьютера. Тексты заявок и
загруженные таблицы не отправляются во внешнее хранилище, страницы не
кэшируются, а временная копия таблицы удаляется сразу после скачивания.
Сохранение успешной заявки в локальную папку `history/` выключено по умолчанию
и включается отдельной галочкой.

Чтобы выбрать другой порт или не открывать браузер автоматически:

```bash
.venv/bin/python webapp.py --port 9000
.venv/bin/python webapp.py --no-browser
```

Терминальный сценарий ниже остаётся доступен без изменений.

## Настройка

Создайте локальный файл конфигурации по шаблону:

```bash
cp config.example.toml config.toml
```

Для каждого сервиса откройте нужный дашборд Grafana или представление
OpenSearch Discover и скопируйте его URL в соответствующий раздел:

```toml
[services.zapis]
url = "https://grafana.example.local/d/...?..."

[services.bff]
url = "https://dashboards.example.local/app/data-explorer/discover#?..."

[services.secretary]
url = "<полная ссылка Grafana Explore>"

[services.noise]
url = "<полная ссылка Grafana Explore>"
```

Для Grafana l2tool сохраняет статические параметры скопированного URL
(например, `orgId`, окружение и кластер) и заменяет значения, относящиеся к
заявке. Для OpenSearch сначала выберите нужное представление данных, затем
скопируйте URL Discover: l2tool извлечёт `indexPattern` и заменит поисковый
запрос и временной диапазон.

Ссылки для `secretary` и `noise` храните только в локальном `config.toml`.
В Git и `config.example.toml` реальные адреса не добавляются. Для двух ссылок
продукта «Звонки» достаточно одного URL в `[services.myconnect]`:
`myconnect_call` автоматически использует тот же tenant и представление данных.
В скопированных Grafana Explore-ссылках оставьте пример номера в обратных
кавычках: при запуске l2tool заменит его номером из заявки. Если в заявке
распознаны дата и время, диапазон Explore также заменяется интервалом из
заявки. При нескольких временах создаётся отдельная ссылка для каждого звонка.
Если время явно пропущено, сохраняется диапазон скопированной ссылки.

Период можно задать отдельно для каждой ссылки OpenSearch:

```toml
[services.sip_stack]
minutes_before = 2
minutes_after = 90

[services.bff]
minutes_before = 5
minutes_after = 120

[services.myconnect]
minutes_before = 10
minutes_after = 60

[services.myconnect_call]
minutes_before = 10
minutes_after = 60
```

Диапазон строится относительно даты и времени звонка из заявки. При нескольких
временах начало берётся от самого раннего звонка, окончание — от самого позднего.
Если параметры не указаны, используются 2 минуты до и 90 минут после звонка.

Локальный `config.toml` игнорируется Git и не должен попадать в коммит.
Прежняя структура конфигурации `[grafana]` и `[opensearch]` по-прежнему
поддерживается.

Создайте локальную директорию для заявок; она также игнорируется Git:

```bash
mkdir -p tickets
```

## Стандартный сценарий работы

Вставьте текущую заявку в файл:

```text
tickets/current.txt
```

Затем запустите:

```bash
python3 gtool.py
```

Поведение по умолчанию:

- читает `tickets/current.txt`;
- предлагает выбрать продукт и его настроенные сервисы;
- использует для Grafana окно в 60 минут;
- если найдена только дата звонка, позволяет оставить интервал 08:00–20:00
  или ввести точные дату и время;
- сообщает об ошибках парсинга вместе с исходной строкой и запрашивает только
  отсутствующие или некорректные поля перед созданием ссылок;
- выводит совпадения из локальной истории;
- выводит сформированные ссылки, не открывая браузер;
- сохраняет локальный YAML-архив в `history/`;
- перезаписывает `tickets/current.parsed.json` нормализованными значениями,
  ссылками и пустым полем `call_uuid` для дальнейшего расследования.

Полезные параметры:

```bash
python3 gtool.py --file tickets/other.txt
python3 gtool.py --open zapis,bff
python3 gtool.py --window 60
python3 gtool.py --no-history
python3 gtool.py --dry-run
```

## Экспорт заявки в JSON

Используйте `--export-case`, чтобы сохранить разобранный контекст заявки и
сформированные ссылки в структурированный JSON-файл для последующей передачи
в `l2-local-ai`:

```bash
python3 gtool.py --file tickets/current.txt --product recording --export-case cases/current.json
```

Экспорт содержит нормализованные идентификаторы, дату и время события,
выбранные сервисы и сформированные ссылки. В него не попадают исходный текст
заявки, необработанные телефонные поля, абсолютные локальные пути, содержимое
конфигурации, токены, cookies и переменные окружения.

JSON-файлы заявок могут содержать номера клиентов и внутренние ссылки.
Директория `cases/` игнорируется Git.

После каждого успешного запуска такая же структура автоматически записывается
рядом с входным файлом. Для `tickets/current.txt` это
`tickets/current.parsed.json`. Исходная заявка не меняется. Файлы с шаблоном
`*.parsed.json` игнорируются Git.

Режим профиля продукта:

```bash
python3 gtool.py --product recording
```

Доступные профили продуктов:

| Профиль | Продукт | Сервисы |
| --- | --- | --- |
| `recording` | Запись | `zapis`, `sip_stack`, `bff` |
| `secretary` | Секретарь | `secretary` |
| `calls` | Звонки | `myconnect`, `myconnect_call` |
| `noise` | Шумоподавление | `noise` |
| `assistant` | Ассистент в звонке | пока не настроено |

Используйте либо `--product`, либо `--open`: эти параметры нельзя совмещать.
Передайте `--open all`, чтобы запустить все настроенные сервисы. Если в
интерактивном терминале не указан ни один из параметров, инструмент покажет
меню выбора продукта. В неинтерактивном режиме по умолчанию используются
`zapis,bff,myconnect,myconnect_call`.

`--dry-run` разбирает заявку и выводит совпадения в истории и сформированные
ссылки, но не сохраняет историю и диагностические данные парсера.

История, автоматический `*.parsed.json` и явно запрошенный `--export-case`
записываются только после полностью успешной обработки. Частичный результат,
когда часть сервисов не смогла сформировать ссылки, выводится в терминал, но не
сохраняется. Код завершения равен `0` при успехе, `1` при частичном результате и
`2` при неуспешной обработке или ошибке аргументов.

Чтобы проверить настройку без реальной заявки:

```bash
python3 gtool.py --file examples/ticket.example.txt --product recording --dry-run
```

## Вторичная диагностика записи по UUID

Поиск в MGW, VSS, CRS и Collector не входит в первичную диагностику продукта
«Запись». Используйте его отдельно, когда UUID звонка уже найден на первом
этапе:

```bash
python3 gtool.py --file tickets/current.txt \
  --open recording_mgw \
  --call-uuid 12345678-1234-5678-1234-567812345678
```

Для проверки всей цепочки обработки записи:

```bash
python3 gtool.py --file tickets/current.txt \
  --open recording_mgw,recording_vss_crs,recording_crs,recording_collector \
  --call-uuid 12345678-1234-5678-1234-567812345678
```

UUID проверяется перед созданием ссылок. Диапазон Loki строится по времени из
заявки; если оно явно пропущено, используется последний час.

## Пакетная обработка потерянных звонков

Отдельный временный режим обрабатывает табличную выгрузку, не меняя обычный
сценарий `gtool.py`. Поддерживаются XLSX, XLSM, CSV и TSV. В исходной таблице
должны присутствовать столбцы:

- `Номер пользователя`;
- `Номер другой стороны`;
- `Старт звонка` — время уже должно быть в UTC;
- `Продолжительность звонка`;
- `Направление звонка` — `in`/`out`, `входящий`/`исходящий` и их английские
  варианты.

Запуск:

```bash
python3 lost_calls_table.py выгрузка.xlsx
```

По умолчанию рядом появится `выгрузка.cleaned.xlsx`. Можно явно указать файл и
лист:

```bash
python3 lost_calls_table.py выгрузка.xlsx \
  --output tickets/потерянные-звонки.xlsx \
  --sheet "Выгрузка"
```

В очищенной таблице остаются только пять перечисленных столбцов и три
кликабельные колонки: `Zapis`, `SIP stack prod` и `MGW`.
Абонентом всегда считается `Номер пользователя` из первого столбца; он
используется как `msisdn` во всех трёх ссылках. Номера не подсвечиваются, а
направление звонка сохраняется только как диагностические метаданные. Для
`SIP stack prod` время из таблицы переводится из UTC в московское. Для всех трёх
ссылок задаётся одно окно: от двух минут до старта звонка до полутора часов после
него. Ссылка `MGW` ищет в логах `mgw.service` оба номера без ведущей `7`.
Звонки, которые старше 5 суток (120 часов) относительно текущего
времени UTC, полностью исключаются из результата. Строки с некорректными
номерами или временем сохраняются без ссылок и перечисляются в предупреждениях
CLI.

## Локальные данные и конфиденциальность

Данные заявки могут содержать номера телефонов и другую чувствительную
информацию. Инструмент локально хранит:

- `tickets/` — текст заявки, предоставленный пользователем;
- `diagnostic_sources.json` — пользовательские диагностические блоки с
  внутренними ссылками Grafana и OpenSearch;
- файлы `*.parsed.json` рядом с заявкой — нормализованные идентификаторы,
  сформированные ссылки и пустое поле `call_uuid`; при каждом запуске файл для
  входной заявки перезаписывается;
- `history/` — YAML-архивы с исходным текстом заявки, разобранными полями,
  сформированными ссылками и номерами телефонов; основной номер также входит в
  имя файла архива;
- `history/index.json` — индекс путей к архивам по номеру телефона;
- `parser_issues/parser_issues.jsonl` — неразобранные исходные строки при
  создании диагностических данных парсера.
- `*.cleaned.xlsx` рядом с табличной выгрузкой — очищенные строки и внутренние
  диагностические ссылки.

Эти пути игнорируются Git. `--no-history` предотвращает создание архива
истории, но не отключает диагностику парсера. Используйте `--dry-run`, если не
нужно записывать ни историю, ни диагностические данные парсера.

## Сервисы

Метаданные сервисов находятся в `services/registry.py`. Сборка URL для каждой
платформы изолирована в `services/loki_explore.py` и `services/opensearch.py`, а
запросы, специфичные для заявок, остаются в `modules/`. Благодаря этому CLI не
зависит от реализации отдельных сервисов. Полная таблица всех одиннадцати
сервисов, включая цепочку вторичной диагностики записи, — в
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md#8-реестр-сервисов-и-модули).

- `zapis` — поиск логов звонков на дашборде Grafana `find-call-in-logs`;
- `sip_stack` — поиск логов SIP stack в OpenSearch по клиентскому `msisdn`;
- `bff` — поиск логов BFF в OpenSearch;
- `secretary` — поиск логов Секретаря в Grafana Loki по номеру клиента;
- `myconnect` — поиск случаев `profile not found` в MyConnect;
- `myconnect_call` — поиск логов MyConnect по присоединённому/проблемному
  звонку с использованием `master:<msisdn>` и участника SIP.
- `noise` — поиск логов Шумоподавления в Grafana Loki по десятизначному номеру.

## Разработка

Установите зависимости для разработки (pytest, httpx для тестов веб-приложения,
ruff) и запустите набор тестов и линтер — то же, что выполняет CI:

```bash
python3 -m pip install -r requirements-dev.txt
python -m pytest -q
python -m ruff check .
```

При изменении архитектуры (слои, потоки данных, хранилища) обновляйте
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). Крупные задумки ведутся по
задачам из [docs/tasks/](docs/tasks), правила ветвления — в
[CONTRIBUTING.md](CONTRIBUTING.md).
