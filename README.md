# l2tool

Локальный инструмент диагностики заявок L2: веб-интерфейс и CLI. Разбирает
текст заявки, нормализует номера, дату, время и регион, после чего формирует
готовые ссылки на Grafana и OpenSearch. Сам инструмент не обращается к этим
системам по API — ссылки открываются в браузере пользователя.

Подробное описание устройства сервиса — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md),
пошаговые сценарии работы — в [docs/USAGE.md](docs/USAGE.md), план развития
веб-интерфейса — в [docs/UI_PLAN.md](docs/UI_PLAN.md).

## Быстрый запуск

Скачайте архив исходного кода со страницы
[Releases](https://github.com/shifter1710/l2tool/releases) (или склонируйте
репозиторий) и запустите:

- **Linux / macOS** — `./start.sh`
- **Windows** — `start.bat` (двойной клик или из терминала)

Нужен только установленный Python 3.10+. При первом запуске скрипт сам создаст
виртуальное окружение `.venv`, установит зависимости и откроет браузер на
`http://127.0.0.1:8765`; повторные запуски стартуют мгновенно. Параметры
`webapp.py` передаются скрипту напрямую: `./start.sh --port 9000`,
`start.bat --no-browser`.

## Требования

- Python 3.10 или новее (CI запускается на Python 3.12)
- доступ к экземплярам Grafana и OpenSearch, настроенным для вашего окружения

Создайте виртуальное окружение и установите зависимости:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

## Локальный веб-интерфейс

Запустите:

```bash
.venv/bin/python webapp.py
```

Браузер откроется на `http://127.0.0.1:8765`. В интерфейсе можно:

- вставить заявку и выбрать профиль продукта;
- проверить распознанные номера, время и регион — рядом с номерами А и Б
  показывается их 16-символьный хеш для поиска в логах BFF;
- исправить отдельные поля, не меняя исходный текст;
- открыть сформированные ссылки Grafana и OpenSearch — каждая помечена, по
  какому значению построена (номер клиента, номер А или Б, UUID);
- отдельно запустить настроенные блоки второго уровня по UUID;
- обработать локальную выгрузку потерянных звонков и скачать готовый XLSX;
- построить ссылки по каждому звонку из истории баланса — панель «История
  звонков · из истории баланса» сгруппирует события переадресации сама.

Если в заявке нет даты и времени звонка, ссылки всё равно формируются:
диапазоны берутся из настроек блоков (относительный `now`-диапазон или период
из ссылки-примера), а в предупреждениях отмечается, что время не найдено.

Раздел «Настройки источников» — это полноценный редактор источников диагностики:

- **Продукты.** Список продуктов редактируется на сайте: добавить свой (ключ,
  название, цвет монограммы), переименовать, удалить. Ключи встроенных
  продуктов (`recording`, `secretary`, `calls`, `noise`, `assistant`) неизменны
  — на них ссылается CLI; сам встроенный продукт можно удалить и при
  необходимости создать заново. Удаление продукта с блоками запрещено — сначала
  удалите или перенесите их.
- **Блоки.** Добавлять, переименовывать, переносить между продуктами и
  уровнями «Поиск по номерам» / «Поиск по UUID», дублировать и удалять. Блок
  можно временно **выключить** — он останется в настройках, но не попадёт в
  диагностику; для продукта есть «включить все / выключить все». Кнопки
  «Выше/Ниже» задают порядок блоков — он же порядок ссылок в результатах.
- **Проверка до сохранения.** В каждой форме блока есть поле «тестовый номер
  или UUID» и кнопка «Проверить ссылку»: l2tool покажет готовый URL с
  подстановкой и текущим временем и ошибки настройки — без записи в файл.
- **Перенос из config.toml.** Кнопка «Перенести сервисы из config.toml»
  превращает секции `[services.*]` с заполненным `url` в динамические блоки
  выбранного продукта (односторонний мост для перехода с CLI; сам
  `config.toml` не меняется).
- **Временные диапазоны блока.** По умолчанию ссылка строится окном
  «минут до / минут после» вокруг времени звонка из заявки. Если заполнить оба
  поля «Диапазон от / до» в формате Grafana (`now`, `now-5d`, `now-2h` …),
  ссылка всегда будет открываться с этим относительным диапазоном — время из
  заявки и минуты игнорируются. Доступно для дашбордов Grafana и OpenSearch.

Для настройки блока достаточно вставить готовую ссылку Grafana или OpenSearch
с тестовым номером либо UUID. l2tool определит тип ссылки и способ подстановки,
а затем будет заменять пример данными разобранной заявки и актуальным временным
диапазоном.

Настройки веб-интерфейса хранятся локально в `diagnostic_sources.json` (схема
v2: каталог продуктов + блоки; старый файл версии 1 открывается без правки и
обновляется при первом изменении). После добавления первого пользовательского
блока для встроенного продукта он заменяет прежний профиль `config.toml` в
веб-интерфейсе. CLI тоже читает эти блоки (см. «Режимы конфигурации CLI»);
`config.toml` остаётся фолбэком для обратной совместимости.

Готовую пользовательскую конфигурацию можно добавить на странице настроек из
файла `diagnostic_sources.json`. Импорт сначала проверяет все блоки, затем
добавляет новые к существующим и пропускает точные дубликаты. Там же можно
скачать текущую конфигурацию для переноса на другой компьютер.

### Все конфиги одним файлом

Панель «Все конфиги сразу» в разделе «Данные» страницы настроек собирает в
один JSON-файл всё: диагностические блоки с номерами Секретаря, справочник
кодов, ранбук и `config.toml`. Загрузка такого файла на другом компьютере
переносит настройку целиком:

- блоки добавляются к существующим, дубликаты пропускаются;
- недостающие продукты из бандла создаются автоматически;
- справочник кодов и ранбук заменяются целиком (как при их одиночном импорте);
- `config.toml` проверяется как TOML и перезаписывается, прежний файл
  остаётся в `backups/`; секреты (ключи `token`/`password`/`api_key`…,
  параметры вида `?token=…`, логин и пароль внутри ссылки) и ссылки
  не-http(s), включая `javascript:`, отклоняются;
- при выгрузке бандла `config.toml` с секретами в файл не попадает —
  сводка состава бандла на странице настроек предупредит об этом.

Каждое хранилище можно переносить и по отдельности: блоки —
`diagnostic_sources.json`, справочник — на странице `/reference`, ранбук —
в панели ранбука, `config.toml` — строка «Статический профиль отдельно».

### Значения по умолчанию в config.toml

Окна, продукты форм и наборы сервисов не зашиты в код — при желании они
переопределяются секциями `[defaults]`, `[gtool]` и `[call_history]` (см.
`config.example.toml`): окно поиска, выбранный продукт основной формы и
панели истории звонков, сколько дней хранит Loki, сервисы CLI без `--open`,
максимум звонков в выводе. Без этих ключей работают встроенные значения.

### Резервные копии настроек

Перед каждым изменением (сохранение или удаление блока, импорт, правка
продуктов, откат) l2tool автоматически сохраняет копию настроек в локальную
папку `backups/` (последние 20 копий). На странице настроек есть список копий с
датой и количеством блоков и кнопка «Откатиться» — например, чтобы вернуть
случайно удалённый блок. Откат сам создаёт копию текущего состояния, поэтому
его тоже можно отменить. Папка `backups/` игнорируется Git.

Сервис принимает соединения только с этого компьютера. Тексты заявок и
загруженные таблицы не отправляются во внешнее хранилище, страницы не
кэшируются, а временная копия таблицы удаляется сразу после скачивания.
Сохранение успешной заявки в локальную папку `history/` выключено по умолчанию
и включается отдельной галочкой.

Чтобы выбрать другой порт или не открывать браузер автоматически:

```bash
.venv/bin/python webapp.py --port 9000
.venv/bin/python webapp.py --no-browser
```

Терминальный сценарий ниже остаётся доступен без изменений.

## Настройка

Создайте локальный файл конфигурации по шаблону:

```bash
cp config.example.toml config.toml
```

Для каждого сервиса откройте нужный дашборд Grafana или представление
OpenSearch Discover и скопируйте его URL в соответствующий раздел:

```toml
[services.zapis]
url = "https://grafana.example.local/d/...?..."

[services.bff]
url = "https://dashboards.example.local/app/data-explorer/discover#?..."

[services.secretary]
url = "<полная ссылка Grafana Explore>"

[services.noise]
url = "<полная ссылка Grafana Explore>"
```

Для Grafana l2tool сохраняет статические параметры скопированного URL
(например, `orgId`, окружение и кластер) и заменяет значения, относящиеся к
заявке. Для OpenSearch сначала выберите нужное представление данных, затем
скопируйте URL Discover: l2tool извлечёт `indexPattern` и заменит поисковый
запрос и временной диапазон.

Ссылки для `secretary` и `noise` храните только в локальном `config.toml`.
В Git и `config.example.toml` реальные адреса не добавляются. Для двух ссылок
продукта «Звонки» достаточно одного URL в `[services.myconnect]`:
`myconnect_call` автоматически использует тот же tenant и представление данных.
В скопированных Grafana Explore-ссылках оставьте пример номера в обратных
кавычках: при запуске l2tool заменит его номером из заявки. Если в заявке
распознаны дата и время, диапазон Explore также заменяется интервалом из
заявки. При нескольких временах создаётся отдельная ссылка для каждого звонка.
Если время явно пропущено, сохраняется диапазон скопированной ссылки.

Период можно задать отдельно для каждой ссылки OpenSearch:

```toml
[services.sip_stack]
minutes_before = 2
minutes_after = 90

[services.bff]
minutes_before = 5
minutes_after = 120

[services.myconnect]
minutes_before = 10
minutes_after = 60

[services.myconnect_call]
minutes_before = 10
minutes_after = 60
```

Диапазон строится относительно даты и времени звонка из заявки. При нескольких
временах начало берётся от самого раннего звонка, окончание — от самого позднего.
Если параметры не указаны, используются 2 минуты до и 90 минут после звонка.

Локальный `config.toml` игнорируется Git и не должен попадать в коммит.
Прежняя структура конфигурации `[grafana]` и `[opensearch]` по-прежнему
поддерживается.

Создайте локальную директорию для заявок; она также игнорируется Git:

```bash
mkdir -p tickets
```

## Сценарии работы

- **Стандартный разбор заявки** — `python3 gtool.py` с файлом
  `tickets/current.txt`: парсинг, предупреждения, готовые ссылки.
- **Экспорт заявки в JSON** — `--export-json` для передачи разбора в другие
  инструменты; режимы конфигурации CLI (`--open`, блоки по id и названию,
  продукты с динамическими блоками).
- **Вторичная диагностика записи по UUID** — `--call-uuid` открывает поиск
  по MGW, VSS, CRS и Collector, когда UUID звонка уже найден.
- **Пакетная обработка потерянных звонков** — таблица XLSX/CSV на входе,
  готовый XLSX со ссылками на выходе (веб-форма или CLI).
- **История звонков из истории баланса** — выгрузка детализации на входе,
  диагностические ссылки по каждому звонку и группировка переадресаций.

Пошаговые инструкции, форматы входных данных и примеры команд — в
[docs/USAGE.md](docs/USAGE.md).

## Локальные данные и конфиденциальность

Данные заявки могут содержать номера телефонов и другую чувствительную
информацию. Инструмент локально хранит:

- `tickets/` — текст заявки, предоставленный пользователем;
- `diagnostic_sources.json` — каталог продуктов и пользовательские
  диагностические блоки с внутренними ссылками Grafana и OpenSearch;
- `backups/` — резервные копии `diagnostic_sources.json` (последние 20);
- `reference_codes.json` — локальный справочник «код → расшифровка»
  (формат — в разделе «Локальный справочник кодов»);
- файлы `*.parsed.json` рядом с заявкой — нормализованные идентификаторы,
  сформированные ссылки и пустое поле `call_uuid`; при каждом запуске файл для
  входной заявки перезаписывается;
- `history/` — YAML-архивы с исходным текстом заявки, разобранными полями,
  сформированными ссылками и номерами телефонов; основной номер также входит в
  имя файла архива;
- `history/index.json` — индекс путей к архивам по номеру телефона;
- `parser_issues/parser_issues.jsonl` — неразобранные исходные строки при
  создании диагностических данных парсера.
- `*.cleaned.xlsx` рядом с табличной выгрузкой — очищенные строки и внутренние
  диагностические ссылки.

Эти пути игнорируются Git. `--no-history` предотвращает создание архива
истории, но не отключает диагностику парсера. Используйте `--dry-run`, если не
нужно записывать ни историю, ни диагностические данные парсера.

## Локальный справочник кодов

Расшифровки внутренних кодов («Decision 10 — …») показываются прямо
в результатах диагностики. Состав зависит от окружения, поэтому реальные
данные хранятся только локально в `reference_codes.json` (Git его игнорирует);
в репозитории есть пустой шаблон `reference_codes.example.json`.

Формат файла — JSON «группа → {код → расшифровка}»:

```json
{
  "Decision": {
    "10": "Абонент вне зоны покрытия"
  },
  "Reason": {
    "42": "Перегрузка MGW"
  }
}
```

Группы — произвольные названия внутренних справочников (до 80 символов),
коды — до 16 символов, расшифровки — до 500 символов, всего не более
1000 записей и 256 КБ. Код в заявке распознаётся по шаблону
«Группа 10», «Группа: 10» или «Группа=10»; попадания схлопываются,
порядок подсказок — как в тексте.

Заполнить справочник можно на странице `/reference` (импорт и экспорт
JSON-файла) или просто создав `reference_codes.json` в корне. Нет файла
или файл битый — приложение работает как раньше, без подсказок;
ошибка формата пишется в лог один раз.

## Сервисы

Метаданные сервисов находятся в `services/registry.py`. Сборка URL для каждой
платформы изолирована в `services/loki_explore.py` и `services/opensearch.py`, а
запросы, специфичные для заявок, остаются в `modules/`. Благодаря этому CLI не
зависит от реализации отдельных сервисов. Полная таблица всех одиннадцати
сервисов, включая цепочку вторичной диагностики записи, — в
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md#8-реестр-сервисов-и-модули).

- `zapis` — поиск логов звонков на дашборде Grafana `find-call-in-logs`;
- `sip_stack` — поиск логов SIP stack в OpenSearch по клиентскому `msisdn`;
- `bff` — поиск логов BFF в OpenSearch;
- `secretary` — поиск логов Секретаря в Grafana Loki по номеру клиента;
- `myconnect` — поиск случаев `profile not found` в MyConnect;
- `myconnect_call` — поиск логов MyConnect по присоединённому/проблемному
  звонку с использованием `master:<msisdn>` и участника SIP.
- `noise` — поиск логов Шумоподавления в Grafana Loki по десятизначному номеру.

## Разработка

Установите зависимости для разработки (pytest, httpx для тестов веб-приложения,
ruff) и запустите набор тестов и линтер — то же, что выполняет CI:

```bash
python3 -m pip install -r requirements-dev.txt
python -m pytest -q
python -m ruff check .
```

При изменении архитектуры (слои, потоки данных, хранилища) обновляйте
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). Выполненные крупные задачи —
в архиве [docs/tasks/done/](docs/tasks/done), правила ветвления — в
[CONTRIBUTING.md](CONTRIBUTING.md).
